# Kuşatma: notes for Claude

Kuşatma is a co-op top-down zombie survival game for the browser (1–20 players, plus PvP), plain ES modules with no build step. Site: https://umvtt.github.io/kusatma/ (GitHub Pages from `main`). How every feature came to be, build by build, with the code names to search for: `docs/HISTORY.md`. **Adding content (classes, zombies, bosses, maps, cosmetics, themes, items, modes): follow `docs/CONTENT.md`**; `test/content.mjs` (in `node test/run.mjs`) and the test repo's `sync70` say exactly what is missing.

## Files
- `index.html`: the page. CSS and `js/main.js` load with `?v=<build>` and an import map gives **every** module `?v=<build>` (add new modules there). Bump all of them with `BUILD` in `js/config.js` on every build.
- `js/config.js`: classes (and their colours `CLASS_COL`), zombies (`ZTYPES` with a `key` each, `ZK` by name, spawn rules `spawn` + `SPAWN_ORDER`, `spawnChance`), weapon paths (`CP`, `weaponOf`), zombies, maps, modes, economy numbers, `BUILD`, protocol `VERSION` (bump it whenever the host↔guest messages change meaning; mixed versions then cannot share a room).
- Host (authoritative simulation, runs in the room creator's browser): `js/host.js` (`HostGame`: players, messages, waves, the step loop, snapshots, backup) with its methods split by subject into mixins added at its bottom: `js/host-combat.js` (hits, damage, abilities, bash, items in use, down/revive), `js/host-zombies.js` (spawning, the zombie brain: `updateZombies` builds the crowd grid and runs `zombieStep` per zombie, which goes through `zombieMove` (a special move under way), `zombieStart` (starting one, and the zombies that move their own way) and `zombieSteer` (walking, unsticking, clawing); separation, hacked allies), `js/host-gear.js` (armory `onBuy`, walls, turrets, drones, mines, dog, blade, pick-ups, map events), `js/pvp.js` (PvP); shared helpers in `js/host-util.js`. `js/client.js` (`ClientGame`: prediction, snapshot apply, effects). `js/render.js` (canvas). `js/world.js` (obstacles, path field). `js/net.js` (PeerJS). `js/live.js` (server socket, accounts).
- Page (build 62 split of the old 2,600-line main.js): `js/app.js` (base, imports no other page module: `$`, `el`, `S`, `renderer`, `IS_TOUCH`, toasts, loading, `ask`, zoom), `js/main.js` (starting/leaving rooms, quick play, host migration, incoming messages, the game loop, graphics level and battery saver, input, tutorial, landing page bits, the live link and invites), `js/lobby.js`, `js/hud.js` (HUD, notices, items in battle, scoreboard, quick messages), `js/shop.js` (armory), `js/over.js` (end screen, share picture, PvP screens), `js/voiceui.js`, `js/esc.js` (Esc menu, settings dialog), `js/chat.js`, `js/acct.js` (sign-in page, dashboard glue, connection test). Code that runs while a module loads may only use `app.js` values or function declarations from other modules (functions are ready before any module runs; `const`s are not). `js/layout.js` (phone layout editor). `js/dash.js` (signed-in dashboard). `js/sfx.js`, `js/voice.js`, `js/scene.js`, `js/settings.js`, `js/consent.js`, `js/catalog.js`, `js/mapgen.js`, `js/perf.js` (performance reports).

## Technical reference (read before touching these)
`docs/TECH.md` holds the details: how a game works (host/guest, snapshots `pack.js`, links, speed), trust rules (anti-cheat, social, groups, owner tools, leaderboard), and the server (Worker `kusatma-api` + Durable Object `Hub`, addresses, live socket, panel actions, rate limits, load, usage dashboard, deploy, limits). The rules that always apply:
- Guests are never trusted: the host clamps hits (`hitCap`) and moves (`moveOk`); the server pays gems and best waves only for waves it can believe.
- Snapshot rows must never hold an object the host keeps changing in place (copy it). Bump `VERSION` whenever host↔guest messages change meaning.
- The Worker source is private and never goes in this repo; deploy keeping bindings (`keep_bindings: ['secret_text']`, Durable Object `HUB` class `Hub`), test in miniflare first, then refresh the test repo's copy (`tools/syncworker.sh`).
- Every response carries CORS headers; keep old requests working; keep the server frugal (every request and storage write counts against the free limits).
- Panel requests are HMAC-signed and work once; never write the panel's address anywhere in the repo.

## Working on it
- After edits: `node test/run.mjs` (parses every module as an ES module, checks content completeness, cheats, snapshots). A plain `node --check file.js` is not enough: it parses as a script and misses module-only errors (e.g. a function declared twice).
- Browser, server and network tests live in the private repo `Umvtt/kusatma-tests` (they know the panel, so never copy them here). Clone it next to this repo, `npm install`, then `node run.mjs` (quick check, ~3 min, after every change) or `node run.mjs --full` (before publishing). It runs the real Worker in miniflare and a local PeerJS server, so co-op tests need no internet. Its `netload` suite models a phone host's weak upload and prints guest freezes per minute: the number the connection builds must bring down. After a server deploy, refresh its Worker copy with its `tools/syncworker.sh`. Every bug the owner reports gets a test there.
- Balance changes: check with quick simulations, not guesses.
- Every update also updates `README.md` (Turkish, player-facing) so it matches the build; check it against the code.
- Commit messages: Turkish title, short player-facing `- ` bullets.
- CSS rules (build 63): `!important` only for `[hidden]`, the owner's spectator view (`body.watching`), reduced motion, pieces the player moved (`.moved`) and the layout editor (`body.ctl-editing`, which must show pieces that are `[hidden]`); anything else wins by its selector. Before removing or rewriting CSS, prove the screens stay the same with the test repo's `cssprint` (fingerprint of every element in 30 screens on 8 screen sizes, compare with `tools/csscmp.cjs`); `cssaudit` and `cssdecl` find rules and declarations that never match or are always overridden (`tools/cssprune.cjs` removes the latter).
- Known debt: rendering speed was only ever measured in headless Chrome (software canvas), not on a phone GPU. `style.css` is still ordered by the build that added each part (later blocks refine earlier ones), not by screen.
