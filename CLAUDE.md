# Kuşatma: notes for Claude

Kuşatma is a co-op top-down zombie survival game for the browser (1–20 players, plus PvP), plain ES modules with no build step. Site: https://umvtt.github.io/kusatma/ (GitHub Pages from `main`). How every feature came to be, build by build, with the code names to search for: `docs/HISTORY.md`.

## How a game works
- The room creator's browser runs `HostGame`; guests send inputs (position, hits, shots) 20×/s and get per-guest snapshots 15×/s over an unordered channel, built against what the guest last confirmed (`p.zh`). Zombie removals repeat until a newer snapshot is confirmed (`zh.seen`/`zh.rm`); guests also drop nearby zombies the host stopped mentioning. Events are numbered and applied once.
- Links (build 59): a guest's snapshot is skipped while more than ~¼ s of data waits on its link (`linkGate` in net.js); the backup goes gzipped and only on an idle link; guests keep zombies walking through short gaps and show `#net-warn` after 1 s; voice is capped at 20 kbps (12 while the host struggles). Performance reports: `js/perf.js` → live `pf` → `Hub.kPerf` → `kp:<day>` → panel Performance (`kperf`).
- Solo games use the same host and client in one page (`OfflineNet`).

## Trust rules (build 58)
- Guests are not trusted: the host clamps each reported hit to the weapon's limit and reach (`hitCap`) and refuses moves faster than the class can go (`moveOk`: one longer jump per 4 s and knockbacks allowed; refused moves bump `p.sp` so the guest snaps back). Anti-cheat reports (`acInput`) still go to the panel.
- The server pays gems and saves best wave only for waves it can believe: one step after the last counted wave of that game (`H.kgw`), or, for a guest, up to what the room's host has reached. Solo games are self-reported by nature; caps (`eco.cap`, `eco.hcap`) limit the damage.
- Panel requests are HMAC-signed with a ±5 min clock window and work once (`H.adSeen`).

## Server
- One Cloudflare Worker `kusatma-api` with the Durable Object `Hub` (SQLite storage, strongly consistent); its source is kept out of this repo (ask the owner for a temporary Cloudflare API token, download the live script, edit, redeploy keeping its bindings: secret `SECRET` and the others via `keep_bindings: ['secret_text']`, Durable Object `HUB` class `Hub`; test locally with `miniflare`).
- Addresses (all forward to the Worker): `kusatma-api.umvtt.workers.dev`, the Deno Deploy app `kusatma-api` (`kusatma-api.umvtt.deno.net`, it exists because Turkish ISPs block *.workers.dev and *.pages.dev) and the Pages project `kusatma-api` (`kusatma-api.pages.dev`). `live.js` tries them in turn; the panel has the same list built in.
- Every response carries CORS headers, even errors; keep old requests working.
- **Live socket and panel tools:** its games connect to the same server at `/klive` (sockets tagged `k`, `kws`; untagged sockets are refused; its `js/live.js` tries the Deno, workers.dev and Pages addresses in turn). The panel's Kuşatma section (`kLoad`; admin actions `kdash`, `kcfgset`, `kmsg`, `kkick`, `kban`, `kunban`) shows live players and rooms, news and maintenance (`kcfg`), bans (`kbans`, by device) and daily stats (`kd:<day>`: players, peak, games, best wave). Optional Kuşatma accounts (`/kacct` reg/login/me/out, `ka:<id>`, name index `kn:<nkey>`, sessions `ks:<token>`; the game's `live.js` keeps `kusatma-hesap` and sends the token in `hi`); account names are locked (`knames`, sent in the Kuşatma cfg as `names`, checked by the game's `nameTaken` with the same `nkey`); leaderboard `/ktop` (cached 5 min, hidden accounts left out). Signed-in Kuşatma players get a full-page panel instead of the menu (`#dashpage`, `dpShow`: home, open rooms, stats, leaderboard); making a room opens a popup (`roomDlg`: open/private, room name, map, difficulty, player limit `HostGame.maxP`); open rooms of signed-in hosts are listed at `/krooms` (from `hi`: `pub`, `rn`, `mx`, `df`; cached 8 s). Sidebar: Dashboard, Logs, then Live, Control room, Events, Schedule, News & settings, Accounts, Economy, Shop, Season, Reports, Moderation, Leaderboard, Stats, Analytics, Data, Bans, and at the bottom Activity, Security, Lock. Tabs: Live, Accounts (`kpl`, accounts only: stats written when a signed-in socket closes (`kEnd`); `kalist`, `kaget`, `kanote`, `kalb` hide from leaderboard, `kapw` reset password, `kadel` delete; bans can be by account), Leaderboard (`klb`), Bans (`kbn`; lifted bans are queued (`unb`/`kunb`) and sent as `unban` when that device or account next connects; a Kuşatma game that thinks it is banned says `bn:1` in `hi` and is cleared at once if it no longer is), Live tools: gold to one player (`kgift` → the room's host gets `gift`, `HostGame.adminGift` by name), message or close a room (`kroom`), account rename (`karen`, frees the old name, pushes `acct` so the game re-checks) and stats reset (`kareset`); Stats adds classes, maps and difficulty per day (`kd` `cls`/`map`/`diff`, from `stat` and the `cls` in `hi`); Events (`kev`: boss or gold; the host's `HostGame.adminEvent` applies it, a boss between waves waits for the next wave via `pendBoss`), News & maintenance, Stats; the room viewer (`kwatch` → host sends `rd` from `HostGame.detail()`, solo games are keyed `s<socket id>`). Activity and Security sit at the bottom of the sidebar, with Lock; the panel opens on the Dashboard.
- **Rate limits (server, in memory only, no storage writes; `Hub.rl`, per player address):** account creation 3/hour, sign-in 10/10 min, `/turn` 20/10 min, live sockets 20/min, `/ping` 30/min, everything else 120/min; the panel 300/min, and 10 wrong admin keys in 10 minutes block that address for 15 minutes (only `reason:'auth'` counts). Answers `429 {reason:'slow'}`. The Deno forwarder passes each player's real address (`x-client-ip` header, or `_ip` in the live-socket URL) signed with a shared key (`FWDK`, only in the private server and forwarder code), so its players are not lumped together. `/ping` is answered before the Durable Object (connection tests cost almost nothing); Kuşatma's Bağlantı testi (`diagRun`) uses it, the live socket's state, the PeerJS service and STUN/TURN candidate checks. The Dashboard also shows TURN relay data (Cloudflare `callsTurnUsageAdaptiveGroups`) against the 1,000 GB monthly allowance.
- **Server load (sized for thousands of daily players on the free plan):** cloud saves upload at most once a minute (`cloudDirty` throttle, `cloudNow` when the page is hidden or closed); settings arrive over the live socket and are only polled while it is down; the room list refreshes every 20 s while open and hosts check in every 30 s (rooms drop 75 s after their last check-in); the server adds up stats in memory and writes them once a minute (`buf`, `alarm`, `flushStats`) and keeps the ban list in memory (`banList`). Keep new features this frugal: every request and storage write counts against the daily free limits.
- **Usage dashboard:** the panel's first tab, Dashboard (`home`, `hLoad`), shows Cloudflare and Deno usage against the free limits (today, this month, 30-day charts, per service) from the admin action `usage`: the server asks Cloudflare's GraphQL analytics and Deno's `/v2/apps/{app}/analytics`, caches it 5 minutes, and needs Worker secrets `CFT` (Cloudflare API token), `CFACC` (account id) and `DDT` (Deno token); without them it says not connected. Deploys keep secrets (`keep_bindings: ['secret_text']` in the upload metadata). The Dashboard is split into a Cloudflare column and a Deno column (limits, today/month numbers, 30-day charts); every bar chart in the panel shows a tip with the day and value on hover or tap (`.ctip`, bars carry `data-tip`).
- Deploy: the private Worker source lives outside the repo (ask the owner for a temporary Cloudflare token if it is not at hand); redeploy keeping bindings (`keep_bindings: ['secret_text']`). Test locally with `miniflare`.
- Known limits: one Durable Object (`Hub`) holds every socket, account index and log; fine for hundreds online, the first thing to split if the game grows. When Cloudflare restarts it, in-memory state is lost (rate limits, `kgw`, `kmr`, `kerr`, `kIdx`); gems not yet saved survive because they sit on the sockets' attachments.

## Working on it
- After edits: `node --check` every changed module, then `node test/run.mjs`.
- Browser, server and network tests live in the private repo `Umvtt/kusatma-tests` (they know the panel, so never copy them here). Clone it next to this repo, `npm install`, then `node run.mjs` (quick check, ~3 min, after every change) or `node run.mjs --full` (before publishing). It runs the real Worker in miniflare and a local PeerJS server, so co-op tests need no internet. Its `netload` suite models a phone host's weak upload and prints guest freezes per minute: the number the connection builds must bring down. After a server deploy, refresh its Worker copy with its `tools/syncworker.sh`. Every bug the owner reports gets a test there.
- Balance changes: check with quick simulations, not guesses.
- Every update also updates `README.md` (Turkish, player-facing) so it matches the build; check it against the code.
- Commit messages: Turkish title, short player-facing `- ` bullets.
- Known debt: `js/main.js` (~2,600 lines) and `js/host.js` (~2,400) still mix many concerns; split pieces out like `layout.js` when touching them. Rendering speed was only ever measured in headless Chrome (software canvas), not on a phone GPU.
